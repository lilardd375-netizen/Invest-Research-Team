## b) 当前架构

整条流水线是「生成 → 批判 → 返工」的循环图：主编出大纲，财务分析 Agent 基于
**真实 akshare 数据**给结论，风控 Agent 以反方辩手身份审查前两者的输出并给
`severity`；路由函数据此决定返工还是成稿。**三个分析节点都是真实 LLM，只有
返工与成稿两个节点仍是占位**。所有 Agent 走同一套重试/降级契约：可重试错误
（坏 JSON、限流、网络）重试 1 次，硬故障（401）直接降级，降级只标记状态、
不中断流程。

```
                          query（如「宁德时代 300750 的投资价值」）
                                     │
                                     ▼
              ┌────────────────────────────────────────────┐
              │ planner                     ★真实 LLM      │
              │ 出 4-6 章大纲 → OutlineModel 校验           │
              └───────────────────┬────────────────────────┘
                                  │ outline
                                  ▼
              ┌────────────────────────────────────────────┐
              │ financial_analyst           ★真实 LLM      │
              │ ← AkshareProvider 取真实财务指标（真实数据） │
              │ → conclusion / key_points / concerns       │
              └───────────────────┬────────────────────────┘
                                  │ analyses
                                  ▼
              ┌────────────────────────────────────────────┐
              │ risk_review                 ★真实 LLM      │
              │ 反方辩手：severity / challenges / summary   │
              │ 同时算 stuck、回写 round_at_last_review     │
              └───────────────────┬────────────────────────┘
                                  │ risk_review
                                  ▼
                    route_after_review()（纯函数，无 LLM）
                    high 且 轮次<2 且 not stuck ?
                         │                    │
                   是 ───┘                    └─── 否
                         ▼                          ▼
        ┌────────────────────────────┐   ┌────────────────────────────┐
        │ revise      ☆占位（无 LLM） │   │ finalize   ☆占位（无 LLM） │
        │ 只做 revision_round + 1     │   │ 目前写死 "stub report"      │
        └──────────────┬─────────────┘   └──────────────┬─────────────┘
                       │                                │
                       └──── ↺ 回到 risk_review          └────► END
```

图例：★ = 真实 LLM（可注入 llm，None 时回退占位）；☆ = 占位节点（本步未实现）。

## c) 已知问题 / 技术债

1. **返工循环空转（最关键）**：`revise_node` 只做 `revision_round + 1`，
   风控的 `challenges` **不会回流给分析师**。于是分析师第二轮输出与前一轮基本一致，
   风控复审必然继续报 high，直到撞上 `MAX_REVISION_ROUNDS = 2` 才成稿——
   返工额度被烧掉但问题没被修。真实冒烟里就是这个形态（连报 2 轮 high）。
2. **行业 / 舆情 / 技术面 Agent 未实现，风控必然报「覆盖不足」**：大纲里有
   6 大板块 18 个研究问题，但只有财务一个 Agent 产出结果，风控会据此判 high
   （冒烟第 7 条 challenge 就是这件事），进一步加剧第 1 条的烧额度问题。
3. **模型知识过期会把最新数据误判为「未来数据」**：系统日期 2026-10-14，akshare 的
   最新报告期 2026-06-30 是真实存在的，但模型的知识截止时间更早，于是质疑
   「报告期在未来、数据来源存疑」（冒烟第 1 条 challenge）。
   这说明风控不盲信数字（是好事），但 prompt 里目前**没有给风控任何时间锚点**
   （今天的日期、`as_of` 是真实披露期还是预测值），导致误判无法自证。
4. **成稿节点仍是占位**：`finalize_node` 写死 `"stub report"`，
   风控的 `challenges` / `summary` 与财务结论都没有被写进最终报告。
5. **单一数据源、单期数据**：只接了 `stock_financial_analysis_indicator` 一个接口，
   没有第二数据源交叉验证；且只在最新一期上做分析，缺历史趋势（毛利率常缺），
   财务结论的稳健性受限。
6. **无持久化 / checkpoint**：langgraph 的 checkpointer 未接，流程中断无法续跑，
   也没有把每次评审结论落盘留痕。
7. **返工上限是硬编码常量**：`MAX_REVISION_ROUNDS = 2`（`src/graph/builder.py:18`），
   调大时需要同时确认 `route_after_review` 与 stuck 保险丝的配合。

## 推送前操作说明（GitHub）

仓库目前**没有配置 remote**，需要先拿到仓库地址再添加。首次推送的完整流程：

```powershell
# 1) 添加 remote（把 <你的仓库地址> 换成 GitHub 上刚建的仓库 URL）
git remote add origin <你的仓库地址>

# 2) 确认 remote 生效
git remote -v

# 3) 演练：不真正上传，只验证连通性（推荐先跑）
git push --dry-run -u origin main

# 4) 确认无误后再真推
git push -u origin main
```

**认证说明**：本机 git 2.40.0 自带 Git Credential Manager。首次 `git push` 时会自动
弹出浏览器登录窗口（或设备码页面），你在自己的 Chrome 里点一下授权即可，
凭据由 Windows 凭据管理器保存，**后续推送无需重复登录**。
整个认证过程不经过对话，**不需要把 API key 或 GitHub token 发给我**。
若浏览器窗口没自动弹出，可以手动执行 `git credential-manager github login` 触发。
